# Pass A1: adversarial audit of the branch that added the HTTP transport

Audited tree: `a2be42a` (branch `http-transport`, one commit on `ed9b40f`), whole module, with the new code
(`http.go`, `http_client.go`, `sse.go`, `client.go`, `app/mcpd/http.go`, `example/http`) first. Date 2026-11-09.
Method: the house audit method (`handbook/audits.md`): four report-only auditors, one skeptic per candidate, fixes,
re-validation. This file is a record of what was found and decided; it is not updated when the code moves.

Labels: **verified** (run, or the exact lines read, by the auditor or skeptic named), **reported** (an agent says it; the
record did not re-run it), **inferred**. Everything attributed to an auditor or skeptic below is *reported* by that agent
unless the line says the recorder ran it.

## How it differed from the handbook

- The auditors (A simplify, B dedup, C correctness+security, D docs) were fresh agents with no build context: the tree,
  the docs, the handbook and a shell. The harness refused A, C and D permission to write their findings files, so those
  three returned their findings as text and B's file was the only one saved. The candidates the skeptics saw are
  condensed from the reports, in the finding form, into a scratch file that is not part of the repository.
- **One skeptic vote per candidate**, not two to four, and no arbiter. 32 candidates were put to a skeptic; the other 27 are
  accounted for below as "not voted" with the reason (two of them, D-1 and D-2, are the same defects as C-7 and C-10 and were
  covered by those votes).
- **The fixes were written by the build session, not by fixers in worktrees**, one finding at a time, test first. Most
  fixes touch the same three files, which worktrees would have made conflict. The fix-skeptic pass is recorded at the
  end of this file.
- Skeptics ran on darwin/arm64 only; nothing here was run on Linux.

## Held for the owner

Each changes behaviour or a guarantee of released code. The recommended answer is the recorder's.

- **H1 (C-9) Queued-request bytes.** `MaxConcurrentRequests*8` requests may queue per session, each holding its parsed params,
  so one session can pin up to ~4 GiB (reported by the skeptic: 7 MiB requests, heap past 4.8 GiB at 350 queued, extrapolated).
  Recommended: a per-session byte budget (`Options.MaxQueuedBytes`, default `MaxMessageBytes*8`, 64 MiB at the default),
  rejecting past it with the existing "overloaded" error. Cost: a client pipelining many large requests now gets errors where
  it got silent queueing.
- **H2 (C-14) Broadcast.** Recommended: a bounded, non-blocking enqueue per session that closes a session that does not drain,
  as the HTTP transport already does; `Session.Notify` itself keeps blocking, because ordering with replies matters there.
  Cost: a wedged peer loses its connection instead of back-pressuring everyone. The comment is already corrected.
- **H3 (C-8) Per-identity session cap.** Recommended: `HTTPOptions.MaxSessionsPerIdentity`, default 0 (unlimited), counted
  under the registry lock. A no-op for anonymous deployments, so it is an enhancement, not a fix.
- **H4 (D-3) mcpd on macOS/BSD.** Recommended: drop `MaxConnsPerUID > 0 ||` from `needCred` in `transport.go` (the per-UID cap
  then degrades to untracked off Linux; the total cap and every explicit credential policy still apply). `harden_test.go`'s
  `TestMaxConnsPerUID` runs only on Linux, so check it there. The docs now state the workaround.
- **H5 (B-2) `jsonrpc` version on stdio/socket.** `jsonrpc.go` says "2.0" is "the only version accepted on the wire", but a
  `"1.0"` or missing-version notification (and batch request) is accepted. Recommended: reject it in `handleFrame` and
  `handleBatch`; leave the Client lenient. Cost: a peer that omits `jsonrpc` on `notifications/initialized` never becomes Ready.
